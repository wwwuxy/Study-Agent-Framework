# 学习计划聊天设计

日期：2026-10-19。状态：用户已确认设计和[实施计划](../plans/2026-10-19-planning-chat.md)，功能与工程验收已完成。

## 1. 目的与已确定的交互

用户希望在学习中通过 Chat 与当前空间的 LLM 沟通，随时修改学习需求，使后续教学计划立即随之调整。用户已选择：**需求明确时自动应用，并展示变更前后**，无需另点“应用计划”。

示例：“每天只有 15 分钟，先学进程调度，例子尽量贴近面试。”聊天完成后，当前空间的时间预算、重点和讲解偏好生效；聊天显示修改摘要与新安排；概览、课堂、报告和 CLI 下一步读取同一份计划。

成功标准是用户的下一次实际学习受到新需求影响，且已有掌握证据、记忆卡片和历史作答可继续使用。聊天记录本身不作为掌握或回忆证据。

延续约束：每个空间强制使用原生 pyBKT＋FSRS；复用所选 BYOK 模型与数据传输授权；PDF 继续使用现有原生模型接口；本次不清空学习数据，不恢复后台正式服务，不做真实付费模型测试。

## 2. 方案比较与选择

| 方案 | 效果与代价 |
|---|---|
| **结构化聊天＋自动更新计划（推荐）** | LLM 理解自然语言并提出受限修改、阶段路线和回复；后端校验、保存，再结合 BKT／FSRS 计算可执行下一步。能够持久生效并保留依据。 |
| 纯聊天回复＋提示词记忆 | 实现较少，但“已调整”的文字不保证影响当前真实计划，重启和跨端容易不一致。 |
| 自由工具调用 Agent 改写所有学习实体 | 可扩展性强，但权限、恢复和数据一致性成本大，超出此次计划聊天所需范围。 |

采用第一种。当前仓库中，LLM 生成课程与教学内容，`planning/policy.py` 计算下一动作，尚无聊天入口。新增聊天理解与阶段路线生成，继续由服务端承担执行、依赖过滤和证据管理。

## 3. 产品范围

### 3.1 聊天可调整的内容

- 当前学习目标的细化、期望深度、目标日期和每日时间预算，沿用现有字段范围。
- 重点知识点与学习顺序；不感兴趣的部分可暂缓，后续仍可重新纳入。
- 讲解偏好，例如更简短、增加例子、面向面试、先解释再练习；这些偏好会进入后续课堂生成上下文。
- 同一空间需要补充的知识内容：允许提出并添加新知识点，以新稳定 key 保存；已有知识点及其历史关联不重命名、不删除。
- LLM 生成有理由的阶段路线，包含阶段目标、关联知识点和建议学习次数；展示为建议而非保证完成日期。

“暂缓”影响当前目标范围，不删除知识点或记忆卡片。若它是当前重点的必要前置，后端会保留该前置的可执行资格并解释原因。完全更换学科可作为新目标提出新的阶段路线和新增节点；原知识与证据保留在该空间，不将旧能力转移为新主题已掌握。

### 3.2 普通沟通与澄清

用户可以询问计划依据，或补充自己的情况。模型返回 `reply`／`clarify`／`update_plan` 三类结果。只有明确的 `update_plan` 且业务校验通过才保存修改。需求不明确时先问一个具体问题；普通交流不反复重写计划。

用户说“这个我已经会了”可作为自述上下文，模型可以建议诊断；不能据此写入 mastered、BKT 参数或 FSRS 到期时间。聊天不直接泄露尚未作答题目的答案。

### 3.3 Web 入口

新增空间内「学习对话」页面，并在概览／课堂提供「调整学习计划」入口。聊天页桌面采用对话区与计划摘要双栏，移动端上下排列；复用现有视觉风格和图标，不增加前端框架。

对话区展示用户／助手消息、生成中／失败状态、多行输入和发送按钮。提供少量可编辑示例，如“今天只有 15 分钟”“先巩固薄弱点”。Ctrl/Cmd＋Enter 发送，输入法组合期间不误发送。单空间同一时刻只处理一个回合。

助手下方的变更卡由服务端结果驱动，显示「已生效」「需要补充信息」「未生效」；列出具体的前后值、路线变化、新下一步及理由。普通回复没有虚假的“已生效”提示。回复完成并提交后立即刷新空间列表、计划、知识地图与当前课堂。

聊天按账号和空间持久保存，分页读取。刷新可恢复历史和未完成回合；切换空间、登出、再登录时，晚到结果不能写入另一个上下文。消息作为文本／受控排版渲染，不执行模型提供的 HTML。

首版在模型生成期间显示等待状态，完整结构校验后一次发布回复和计划；不以打字动画冒充逐 token 输出。后续可以独立增加原生流式适配。

## 4. 计划、课堂与算法的一致性

将“持久学习意图／模型生成路线”与“根据当前证据计算的下一动作”区分保存：`LearningIntent.version` 是需求版本，`LearningPlan.data.version` 继续表示调度策略版本，计划另外返回 `intent_version`，两者不能混用。

1. Chat 给出允许字段的意图修改和路线。
2. 后端校验字段、概念归属、完整图的 DAG、引用范围和阶段关联。
3. 保存版本化意图／路线；新增知识点初始化 BKT unknown 与 FSRS unassessed。
4. 调度器结合最新能力、FSRS 到期、先修条件、目标范围与重点重新推荐。
5. 聊天回复、版本记录、需求变更事件、计划快照同事务发布。

`save_plan()`、GET plan、next-action、报告和教学生成统一读取最新意图。作答后的计划重算只更新动态任务，不覆盖 LLM 阶段路线与偏好。模型路线不是一份跳过先修、忽略真实到期状态的强制执行清单；后端若调整建议顺序，展示具体依据。

优先级作为推荐评分的一个可解释项；目标范围包含其必需前置。暂缓范围的卡片仍保存在复习列表；它们不强制挤占当前目标的下一步，列表标注当前目标外。FSRS 的卡片参数、日志和 due 不因聊天变化而重算。

### 4.1 未完成课堂

目前 `unfinished_lesson()` 会覆盖其他推荐。新增显式课堂状态以支持暂存，不使用 completed 伪装完成：

- 只调整时间或表达偏好：保留当前课堂，后续新内容使用新偏好；已有课堂不静默重写。
- 用户明确切换当前学习内容，且旧课堂不再属于当前安排：将旧课堂标为 paused，保留题目、答案和阅读状态，立即允许按新计划生成内容。
- 未完成复习被暂存时，复习会话标为 paused 并释放活动会话占位；没有新作答就不增加 FSRS 日志、不延后到期。
- 提供暂存课堂列表与继续入口。恢复前检查是否还有其他活动课堂；不会同时创建两个活动课堂。恢复、继续答题沿用原始题目与幂等规则。

聊天不会将暂存课堂计为完成。已经记录的作答仍有效；原课堂内容不因路线修订而丢失。

## 5. 持久化与接口

通过新迁移 0005 增量增加数据结构；既存空间的默认意图等价于当前行为，常规启动不触发模型、不重排既存计划、不清空数据。

- `ChatTurn`：用户／空间归属、幂等键及摘要、用户消息、助手消息、处理状态（processing／completed／failed／conflict／cancelled）、租约、模型／审计引用、结构化结果、基线版本和时间。处理中设置唯一的 active_space_id，结束后清空；每次认领租约 180 秒，发布核对认领 token。用户文本不复制进普通请求日志或 AgentRun。
- `LearningIntent`：每空间唯一的当前需求、范围／重点／偏好、路线和单调版本。
- `PlanRevision`：关联回合、前后版本与需求／路线快照、变更摘要和原因；不复制完整作答或教材正文。
- `Lesson.status`：active／paused，已有记录默认 active；真正完成仍使用原有阅读＋练习证据。ReviewSession 增加 paused 业务状态。

所有新增实体以复合归属外键约束用户／空间，配合空间内幂等键和活动回合唯一约束。空间永久删除与维护清空服务增加新表的依赖删除顺序，禁止迟到模型响应恢复已删除聊天或学习内容。

建议 API 均位于 `/api/v1/study-spaces/{space_id}`：

| 接口 | 用途 |
|---|---|
| GET /chat/turns?before=...&limit=... | 分页历史，包含未完成回合；稳定顺序与 cursor |
| POST /chat/turns | content、idempotency_key、retry=false；处理自然语言、自动应用清晰需求并返回权威状态、变更前后与计划 |
| GET /chat/turns/{turn_id} | 读取处理中／已完成／失败回合，支持刷新和重复请求恢复 |
| GET /plan/revisions?before=... | 分页查看计划变更记录，不在读取时调用模型 |
| GET /lessons/paused | 暂存课堂列表 |
| POST /lessons/{lesson_id}/resume | 幂等恢复已有课堂，检查活动课堂冲突 |

POST 成功新回合返回 201；相同键与内容返回既有回合（处理中的回合返回 202）；相同键不同内容 409。幂等摘要包含空间和 content，retry 仅控制恢复方式，不改变消息身份。失败回合保留用户文本、脱敏错误与重试入口；原键设置 retry=true 后可在失败／过期租约后重试，不重复创建消息或计划版本。并发的不同键若已有活动回合则返回 409，前端提示等待。租约失效后的旧调用即使返回也不能发布。

请求、模型结构化输出和新增公开响应均使用 Pydantic 模型。单条用户消息 1–4000 字符、助手回复最多 8000 字符；历史页默认 30 条、最多 100 条；模型上下文最多最近 20 个成功／澄清回合和当前消息。历史文本总预算 24000 字符，超出时从最旧完整回合起剔除，不丢当前持久需求。路线最多 12 阶段，每阶段最多 30 个 concept key；单回合最多新增 12 个知识点。修改仅限第 3.1 节白名单，日期、数字、key、总图和来源检查由后端执行，禁止任意 JSON patch 或 SQL／代码工具。

CLI 本次不增加交互聊天终端，但其现有 plan／next／learn 自动读取同一更新；接口为后续 CLI chat 保留复用能力。

## 6. 模型调用、并发与故障

复用当前 Provider Adapter 的结构化生成接口，使用当前空间已检测模型；不增加第二套 API Key 配置。不要求服务商支持 tool calling，已有兼容聊天和原生文件模型均能接入。显式 FakeAdapter 增加固定计划聊天场景用于测试与演示；真实模型失败不回退到演示。

上下文只包含该空间的近期有限聊天、当前需求／路线、知识点、能力摘要、复习摘要和当前任务；不加载全用户历史、API Key、题目答案、其他空间信息或所有教材正文。教材片段继续使用现有授权与出处约束，不借聊天扩大文件上传或通用知识补充授权。

一次回合按三个阶段运行：

1. **准备短事务**：鉴权和空间权限检查，串行认领幂等回合，捕获当前意图版本、知识结构指纹、当前模型配置指纹和必要纯数据上下文，提交后释放写锁。
2. **模型阶段**：纯数据输入，结构化 LLM 调用有现有总时限／重试和用量审计；不持有用户行锁或 SQLite 全局写锁，不持有跨线程 ORM Session。
3. **发布短事务**：在独立受控 DB 阶段按固定顺序获取用户／空间／回合锁，重新校验权限、未删除／归档状态、维护标记、认领租约、模型与意图／课程基线。合法后按最新学习证据生成实际下一步并原子提交。

同步 DB 阶段及锁等待在线程内执行，由该线程创建和关闭自己的 Session，避免再次阻塞 ASGI 主循环。SQLite 应用锁仅覆盖对应短 DB 阶段，不包住远端等待；与现有写入口保持一致的锁顺序。

模型等待期间允许继续作答，发布时读取最新 BKT／FSRS，不把旧能力快照覆盖回去。等待期间若另一个计划调整、教材发布改变知识图谱或模型配置改变，则回合返回明确冲突，计划不修改；用户可基于新上下文重试。模型等待期间删除／归档空间或撤销会话，不能发布新的聊天正文或计划。

进程退出导致的处理中回合由有界租约识别，刷新后可重试；不在普通启动时静默发起有费用的模型调用。失败时保留原有效计划，回复状态显示未生效，不能仅展示模型“已调整”字样。发布结果含变更 ID，UI 刷新失败后可通过历史与既有回合恢复已提交结果。

## 7. 实现边界

- 新增 `chat/` 服务模块，分别承担读写／幂等、上下文、模型输出和计划应用；新建 chat API 与 schemas 文件。
- 新增 `planning/intent.py` 负责范围、重点、偏好与路线读取，避免继续扩张主 orchestrator。
- 定向修改 policy、plan 序列化、teaching 生成上下文与课堂恢复，不重写原生 BKT／FSRS 算法。
- 从 `call_model` 提取可复用、无数据库副作用的结构化调用部分；现有教学／评分调用保持既有错误与审计契约。
- 新建 Web `PlanningChat` 及小型状态 helper，接入导航和概览／课堂入口；复用账号／空间失效隔离和样式。
- 增量更新空间删除／清空、迁移、API／OpenAPI、双语 README 与中文使用说明；不引入新产品依赖。

## 8. 验收与测试

1. 明确需求自动生效，变更卡展示真实前后值；普通聊天与含糊需求不写新计划版本。
2. 调整预算、日期、重点、讲解偏好及新增内容后，实际下一步和新生成课堂反映新需求；作答后重算不丢需求和路线。
3. 未满足先修不能被聊天跳过，暂缓依赖有解释；默认全空间行为兼容既有计划。
4. 聊天前后 BKT 可靠证据数、既有 FSRS 卡片与日志不变；新概念为 unknown／unassessed。
5. 修改重点能暂存当前课堂／复习，恢复后使用原题；不会伪造完成、重复作答、重复调度。
6. 多账号／多空间读写隔离，分页稳定；切换／登出／刷新／晚到响应不串记录。
7. 双击、重试、断线恢复、相同键冲突、租约过期、模型失败／非法输出与发布回滚都不重复应用。
8. 在一个 ASGI 事件循环内，用真实临时 PostgreSQL 控制模型等待与并发作答／教材发布／删除；健康检查保持响应，过期上下文不能覆盖新数据。SQLite 验证同类可执行场景。
9. 既存 0004 数据升级与 metadata check 通过，永久删除包含聊天与修订；真实用户库不用于测试，不执行再次清空。
10. 前端行为测试、完整后端回归、生产构建和 1440／390px 隔离演示验证通过。用 Fake／协议替身验证兼容模型路径；没有真实付费 Key 验收就如实保留质量边界。

## 9. 自审与下一步

自动应用方式与此设计均已由用户确认。无待定参数、未命名实体或隐式删除操作；动态调度、LLM 路线和历史证据的责任分开。特别覆盖了既存未完成课堂优先恢复、长模型调用占锁、作答后路线丢失、删除期间迟到发布四项交互风险。

用户审阅此设计后编写实施计划，再按选定方式实现。当前工作区已有未提交 M2／M3 代码，设计提案单独保存，不重置、清理或打包提交既存改动。
